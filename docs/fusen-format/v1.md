# Fusen Format v1

This document specifies the file format Fusen uses to store fusen on Markdown documents.
It is intended for anyone who wants to read or write these files: tool authors, scripts, and AI agents.

The key words "MUST", "MUST NOT", "SHOULD", and "MAY" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

A **reader** is any program that reads a review file. A **writer** is any program that creates or modifies one.

## 1. Files

### 1.1 Location and naming

Review files live in a `.fusen/` directory at the project root, which is the directory where `fusen` is run.
Inside `.fusen/`, each review file mirrors the path of its document relative to the project root, with `.fusen.yaml` appended to the file name.

```
proj/                            ← project root
├── .fusen/
│   ├── README.md.fusen.yaml     ← review file for README.md
│   └── docs/
│       └── spec.md.fusen.yaml   ← review file for docs/spec.md
├── README.md
└── docs/
    └── spec.md
```

### 1.2 Encoding and YAML

- Files are UTF-8 without a BOM, use LF line endings, and end with a newline.
- Files MUST NOT use the following YAML 1.2 features: anchors and aliases (`&`, `*`), tags (such as `!!str`), or multiple documents (`---` separators).
- Readers MAY reject files that use these features.

## 2. Format

### 2.1 Top level

```yaml
version: 1
document: docs/spec.md
fusen:
  - ...
```

| Key | Type | Required | Description |
|---|---|---|---|
| `version` | integer | ✓ | Major version of the format. `1` for this specification. |
| `document` | string | ✓ | Path to the document, relative to the project root, using `/` as the separator. |
| `fusen` | Fusen[] | ✓ | List of fusen (see [2.2](#22-fusen)). |

### 2.2 Fusen

```yaml
- id: 01K5XQ3M8ZJ4T7R2N9B6W1C0VE
  kind: comment
  status: open
  body: Mention that PKCE is required.
  anchor:
    quote: authenticated with **OAuth 2.0**
    lines: 5-5
  docHash: 1db15a510bae93d7861227fa25fabddf3a40692c
  createdAt: 2026-09-24T17:03:00+09:00
```

| Key | Type | Required | Description |
|---|---|---|---|
| `id` | string | ✓ | Identifier, unique within the file (see [2.2.1](#221-id)). |
| `kind` | string | ✓ | Kind of fusen (see [2.2.2](#222-kind)). |
| `status` | enum | ✓ | `open` or `closed`. |
| `body` | string | ✓ | Text of the fusen. MAY be interpreted as Markdown. MUST NOT be empty. |
| `anchor` | Anchor | | Range of the document the fusen refers to (see [2.3](#23-anchor)). **If omitted, the fusen applies to the whole document.** |
| `docHash` | string | ✓ | Hash of the document at the time the fusen was added (see [2.2.3](#223-dochash)). |
| `createdAt` | timestamp | ✓ | RFC 3339 timestamp with a time zone offset. |
| `replies` | Reply[] | | Replies to the fusen (see [2.4](#24-reply)). |

#### 2.2.1 id

- Matches `[A-Za-z0-9_-]{1,64}`, and is unique among all fusen and replies in the file.
- Readers MUST NOT assume any meaning in the format of an ID, such as ordering.
- Fusen generates [ULIDs](https://github.com/ulid/spec).

#### 2.2.2 kind

- Matches `[a-z0-9_-]{1,32}`.
- Only the ID is stored in the review file. Display names and descriptions of kinds are defined in the Fusen settings file (see [Fusen Config Format v1](../config-format/v1.md)), where users can also add their own kinds.
- Fusen ships with two built-in kinds:

| ID | Meaning |
|---|---|
| `comment` | Feedback on the document. |
| `question` | A question about the document. |

- Readers MUST NOT reject fusen whose kind they do not know. Such a kind SHOULD be displayed by its ID.

#### 2.2.3 docHash

- The git blob hash of the document file's raw bytes: the same value as `git hash-object <file>` (SHA-1, 40 lowercase hex digits).
- It is computed as the SHA-1 of `"blob " + <size in bytes, as a decimal string> + "\0" + <content>`.

### 2.3 Anchor

An anchor identifies a range in the document's **source text**, not in the rendered output.

```yaml
anchor:
  quote: authenticated with **OAuth 2.0**
  lines: 5-5
```

| Key | Type | Required | Description |
|---|---|---|---|
| `quote` | string | ✓ | The exact source text of the range. MUST NOT be empty. |
| `lines` | string | ✓ | The lines that contain `quote` (see [2.3.1](#231-lines)). |

- Because `quote` is taken from the source, it may contain Markdown syntax such as `**`, `[text](url)`, or code fences.
- A range may span multiple lines and blocks.
- Writers MUST NOT modify an anchor automatically, for example when the document changes.

#### 2.3.1 lines

- Written as `<start>-<end>`. Line numbers start at 1 and the range includes the end line. A single line is written as `5-5`.
- The start line contains the first character of `quote`, and the end line contains its last character.
- Lines are separated by LF. A CR before an LF is not part of the line. Lines are counted over the whole file, including any front matter.
- Line breaks inside `quote` are stored as LF.

### 2.4 Reply

A reply to a fusen, from a person or an AI agent.

```yaml
replies:
  - id: 01K5Y2A7C9E1G3J5K7M9P1R3T5
    author: claude-code
    body: Added "PKCE is required for all clients." after line 5.
    createdAt: 2026-09-24T18:15:00+09:00
```

| Key | Type | Required | Description |
|---|---|---|---|
| `id` | string | ✓ | Identifier, in the same format as a fusen `id` (see [2.2.1](#221-id)). |
| `author` | string | ✓ | Name of the person or agent who wrote the reply. |
| `body` | string | ✓ | Text of the reply. MAY be interpreted as Markdown. MUST NOT be empty. |
| `createdAt` | timestamp | ✓ | RFC 3339 timestamp with a time zone offset. |

### 2.5 Full example

Document `docs/spec.md`:

```markdown
# Authentication

## Overview

API requests are authenticated with **OAuth 2.0**.

Access tokens are stored on the server side.
Refresh tokens are rotated on every use.

## Error handling

TBD
```

Review file `.fusen/docs/spec.md.fusen.yaml`:

```yaml
version: 1
document: docs/spec.md
fusen:
  - id: 01K5XQ3M8ZJ4T7R2N9B6W1C0VE
    kind: comment
    status: open
    body: Mention that PKCE is required.
    anchor:
      quote: authenticated with **OAuth 2.0**
      lines: 5-5
    docHash: 1db15a510bae93d7861227fa25fabddf3a40692c
    createdAt: 2026-09-24T17:03:00+09:00
    replies:
      - id: 01K5Y2A7C9E1G3J5K7M9P1R3T5
        author: claude-code
        body: Added "PKCE is required for all clients." after line 5.
        createdAt: 2026-09-24T18:15:00+09:00
      - id: 01K5Y2F4H6K8M1P3R5T7V9X2Z4
        author: alice
        body: Thanks. Please also mention the S256 method.
        createdAt: 2026-09-24T18:20:00+09:00
  - id: 01K5XQ7F1Y0S3H6D9K2M5P8R4T
    kind: question
    status: open
    body: |-
      How long are refresh tokens valid?
      Should mobile and web use different lifetimes?
    anchor:
      quote: |-
        Access tokens are stored on the server side.
        Refresh tokens are rotated on every use.
      lines: 7-8
    docHash: 1db15a510bae93d7861227fa25fabddf3a40692c
    createdAt: 2026-09-24T17:06:30+09:00
  - id: 01K5XQB9C4V7X0Z3A6E9G2J5M8
    kind: comment
    status: closed
    body: Error handling needs more detail.
    docHash: 1db15a510bae93d7861227fa25fabddf3a40692c
    createdAt: 2026-09-24T17:10:00+09:00
  - id: 01K5XQD2F6H9K3N7Q1S5V8X2Z4
    kind: question
    status: open
    body: Should this document also cover token revocation?
    docHash: 1db15a510bae93d7861227fa25fabddf3a40692c
    createdAt: 2026-09-24T17:12:00+09:00
```

The first fusen has two replies. The third and fourth fusen have no `anchor`, so they apply to the whole document.

## 3. Rules for writers

### 3.1 Canonical form

Writers SHOULD produce output in the following form:

- Indent with two spaces.
- Order keys as listed in the tables of this specification.
- Omit optional fields that have no value instead of writing `null`.
- Write strings that contain line breaks as literal block scalars (`|` or `|-`).
- Sort `fusen` and each `replies` list by `createdAt` in ascending order, so that new entries are appended at the end.

### 3.2 Preserving unknown fields

- Readers MUST ignore keys they do not recognize, at any level (top level, Fusen, Anchor, or Reply).
- Writers MUST preserve such keys when writing the file back.

### 3.3 Concurrent writes

- Writers SHOULD re-read the file immediately before writing and apply their changes per fusen or reply `id` (read-modify-write).
- Writers SHOULD write to a temporary file and atomically replace the original with a rename.
